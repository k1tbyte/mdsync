# Sync integrity

Breaking one of these silently corrupts user data or publishes remote deletions; every change here needs a test. Map, flows and accepted limits: `features/sync/README.md`. Hunks: `.claude/rules/hunks.md`; history and GC: `.claude/rules/history.md`; platform behavior: `.claude/rules/vault-io.md`; live editing: `.claude/rules/live.md`.

## Baseline and remote reads

- The baseline moves only for paths an operation actually wrote (`advanceBaselineForPaths` in `features/sync/remote/baseline.ts`). Adopting a whole published or remote manifest claims every file this device never downloaded, and the next push publishes them as deletions.
- A pull advances the baseline for `written`, never for the asked paths (an undownloaded conflict would turn into a local edit pushed over the remote); a hunk pull only on a full selection (`isFullSelection`).
- A batch stopped by an error keeps what landed: pull and auto-merge save the baseline, then throw (`PullResult.failed`), as a cancel stops; moves record each as it lands. On the old baseline a landed file reads as this device's edit, and a change made elsewhere meanwhile is pushed back.
- A remote read is complete: equal snapshot ids do not make a partial baseline a remote manifest. A 304 serves only the complete cached response of the same storage adapter, key and root (`fetchRemoteManifest`); a stale read is replaced only by a head this session published, never by the baseline (`reconcileRemoteAgainstBaseline`).
- Every file content read and write goes through `features/sync/content/` (`loadContent`, `storeContent`): the owner of the object format. Bytes it rebuilds (a described blob, a decoded drawing, joined chunks) are checked against the file hash, and a header it does not know makes the content unreadable, never guessed. A root is `objects/<hash>` or `recipes/<hash>` (`readOrder` looks where the size says first); a missing chunk throws, never reads as an absent file. A pull takes a chunk from the file's copy on disk only by its id (a MAC of its bytes), and the joined file is still checked against its hash.
- Upload before publish: a manifest naming objects never uploaded dangles, so a cancelled push publishes nothing (`pushPaths`; uploaded blobs stay).

## Scope and unreadable

- Unreadable is not absent: a file or directory the scan could not read goes to `snapshot.skipped` / `unreadableDirs` and out of the diff (`diff` in `features/sync/changes/diff.ts`, `safeList` in `features/sync/scope/scanner.ts`). Read as missing, a locked file is published as a deletion.
- Empty folders merge three-way (`mergeFolderArrays`): one the baseline knew stays published only while both sides have it, so a deletion on either side propagates; a pull never recreates one deleted here since the baseline (`syncFolders`); one in or under an unreadable directory, or this disk cannot open or name, is kept (`foldersToPublish`); another space's leave the manifest (`scope.owns`).
- Disabled scope is untouched: excluded configuration files and empty folders stay in the remote manifest and baseline during ordinary operations; only an explicit category reset forgets their baseline.
- Plugin code is a filter, not a category: with `syncPluginCode` off (the default) `pluginConfigs` includes only `<configDir>/plugins/<id>/data.json` and descends no deeper than `<id>/`, so code stays frozen like a disabled category (`isConfigAllowed`, `canDescendConfigDir` in `features/sync/scope/scope.ts`). `getCategory` still files code under `pluginConfigs`: an older client resets by that key, and a category of its own would read as remote deletions there.
- Configuration resets are not file deletions: generations are scoped by `<configDir>/<category>`; a newer one makes every device forget that category's baseline files and folders (`reconcileBaselineResetGenerations`) and keep its local files. Ordinary publishes retain generations; every manifest carries `MANIFEST_VERSION` (3), so a client from before resets refuses one (`features/sync/operations/config-reset.ts`).
- A name this disk refuses is skipped, never written (`diskRefuses`): one failed write would stop every pull. Such remote files go to `snapshot.skipped` (`features/sync/changes/remote-names.ts`), such folders are not claimed on disk, a restore leaves them out.
- A drawing is its scene: the scanner fingerprints an Excalidraw file into `scene` (`core/drawing/scene.ts`) and the diff takes equal scenes for equal content (`sameContent`), or every save pushes. Conflicts merge by element (`mergeDrawings` in `core/drawing/merge.ts`, called from `features/sync/apply/conflict-merge.ts`), never by lines: that yields a scene that no longer opens. Notes above the data changed on both sides stay a conflict.
- Auto-merge takes only `.md` (`settleConflict` in `features/sync/apply/auto-merge.ts`): a line merge of JSON or plugin code can be clean by lines and broken as a file, silently mixing two plugin versions. Every other conflict waits for a person.

## Publishing

- A push is done only when its own id reads back: `publishManifestWithGuard` re-reads while it sees a head it replaced; anything but our snapshot id is a `ConcurrentPushError`, so the baseline stays put and the runner re-compares. Taking a replaced head as a stale read lets a sibling's overwrite turn our files into remote deletions.
- Only the head vouches for a blob: a push skips an upload when the head names the hash, or when this device uploaded it for a push never published (`features/sync/remote/uploads.ts`, `UPLOAD_TRUST_MS` 12 h, still probed). Anything else may be swept between probe and publish, so it is uploaded again. A chunk is skipped when the compared HEAD's recipe for the path names it, or this device uploaded it (probed); a recipe is always PUT, after its chunks, so a root present means its chunks landed (`storeContent`). A root that leans on HEAD's chunks stands only under that HEAD, so it stays out of the upload log and a resumed push stores it again; the log keeps the newest `UPLOAD_LOG_MAX` (20 000) entries.
- No automatic push publishes a bulk deletion: more local deletions than `bulkDeleteLimit` (moves excluded) are all held back from every automatic push, logged and reported once per set (`createAutoPushSelector` in `features/sync/automation/auto-push.ts`); the rest still pushes. Only a push by hand, or **Ask before pushing many deletions** (`confirmBulkDeletes`) off, publishes them. The selector also leaves out slow files being edited and files a history restore left (`RestoredFiles`), both ends of a move with them.
- Authorship is set only at publish: `publishFileMap` runs `attribute` (`features/sync/identity/authors.ts`): a changed hash takes the publisher, anything else keeps its parent's `by`. The `authors` table only grows, so an index from any earlier manifest or baseline names the same key; `by` is never content, so equality checks ignore it (`sameEntry`).

## Spaces

- Every path belongs to exactly one space: `spaceOf` picks the deepest root holding it, else the vault. A scope owns its root's subtree minus nested roots (`nestedRoots`). A share's root folder is its mount point, in no space: never published, never removed.
- The vault treats share roots like a local ignore: its entries there stay frozen until its next push leaves them out of the manifest (`ownedFiles` in `features/sync/remote/foreign.ts`); frozen, they would hold the folder's blobs for good. The push record still lists them `deleted`, so history GC sweeps the blobs once no record names them; the Trash tab and a vault restore skip paths the vault no longer owns.
- A baseline forgets frozen entries the remote no longer has (`forgetDroppedForeign`, every refresh), so closing a share never reads them as remote deletions; entries the remote still lists stay, so an edit made before closing is a plain modify. A forgotten entry whose share has no baseline of the path yet moves to the vault slot's `shareBases` (`heldShareBases`): never part of the baseline, gone once the share holds the path or the folder is the vault's again.
- The partition is fixed per refresh: a full refresh asks `host.spaces()` once inside the queue, pulling records first; a targeted share refresh keeps the previous partition; vault signals always ask for a full one. `openSession(space, partition)` builds scopes from that list alone (`sessionFiles` in `app/session-factory.ts`): a record arriving mid-cycle must not turn a root into unscanned vault content that a push publishes as deleted.
- Automatic operations reuse a comparison only inside that serialized cycle, with a matching scope epoch and local-file revision (`runOperationNow`). Hidden configuration files are rescanned every time: their writes emit no vault events.
- A share never publishes the loss of all its files: when its scan holds none of the files its baseline does (folder deleted or moved away here, or back holding only new files; a skipped file counts as there), `compare` throws `SpaceGoneError` (`assertSpacePresent` in `features/sync/remote/space.ts`): the share is that device's error, never an empty folder for everyone. `controller.settleGone` settles it, asked by `features/spaces/ui/space-gone.ts`: Restore forgets the share's state, Delete pushes with `Space.goneAccepted` for that one operation. The vault is not guarded.
- Closing a share is a record edit, never a deletion of files: the record is tombstoned (`closeRecord`: `closed`, rev raised by `CLOSE_REV_STEP`) so no device republishes it, and its root returns to the vault scope with its files from the next refresh. Stop sharing then empties the share's own storage through the operation queue (`deleteShareObjects` refuses the vault).
- Every close (here or seen elsewhere) and leaving shares with the vault storage forget the share's state by its id (`forgetShare`, `StorageState.space`), needing no session: a participant's slot keeps one identity across re-accepts, and a later reopen at any root would read the old baseline as deleted files. Stop sharing refreshes before it deletes (`closeHere` in `features/spaces/ui/share-action.ts`), so an operation queued for the share is refused instead of pushing its objects back.
- A paused share stays in the partition: `spacesOf` marks it `paused` (device-local `settings.pausedSpaces`, `record.paused` published for every device, or shared folders off); the refresh skips it and every session refuses it, reads such as history too (`OperationRunner.openSession`, `openShare`), but its root stays out of the vault scope. Dropping it from the partition would hand the folder to the vault and publish it there.
- A moved root moves on every device before any scan: renaming a share root (or a folder above it) edits the record (`moveRoot`, rev + 1), cancels the running operation and invalidates in the same tick (`scheduleScopeRefresh`); results begun before are dropped (refresh epoch), so auto-push never acts on the old partition. A device that learns of the move keeps the folder where it is (`settings.localRoots`) and `createMoveFollower` (`features/spaces/share-moves.ts`) moves it inside `host.spaces()`, before the partition is fixed. A blocked move keeps the share syncing at the old root; a closed share's folder is the vault's and never moved. An old root must never turn into vault content that holds the share's files.
- A space's remote paths are relative to its root; local ones never are: manifests, history records and pins are translated only in `features/sync/remote/space-paths.ts`, called from `features/sync/remote/manifest.ts`, `features/sync/history/remote.ts`, and `features/sync/history/pins.ts`; every read and write of those blobs goes through it, hash-only readers included. Each scan carries forward the hash-cache entries its space does not own, so one space's persist never drops another's. A share's slot of the state file records its root (`StorageState.root`); `projectSession` re-roots a baseline once after a move (`manifestMoved`), and an unmoved baseline keeps its reference so the persister still debounces.
- Vault-wide listings stay inside `objects/`, `recipes/`, `chunks/`, `pins/` and `history/`: shares live under `<prefix>/shares/<id>/`, records under `<prefix>/spaces/` and `<prefix>/links/`, inside the vault's prefix. GC, verify and reset never list or delete beyond their own folders.

## Moves

- A rename carries its hashes: the scanner trusts a cached hash while size and mtime match, so a rename moves the entry with the file (`StatePersister.carry`, fed by `registerHashCarry` in `app/events.ts`, applied before any read of the state).
- A move acts whole: `pairMoves` (`features/sync/changes/moves.ts`) pairs a gone path with a new one of the same baseline hash in one space (else by file name, only where one to one); anything unclear stays a delete plus an add. The other side's edit of the old path follows the file instead of conflicting.
- Push, pull and revert take both paths when asked for one (`withMoves`, `pullMoves`). A pull renames (`renameLocal`), never over a file that appeared at the new path since the compare; folders it emptied go (`removeEmptied`), never the space root nor one the remote keeps. A revert restores the source and trashes the destination, each only if unedited since the compare. Diff views of a move apply no hunks (`.claude/rules/hunks.md`).
- A rename the disk refuses leaves the move waiting with a warning and the rest of the pull lands; a file left under its step name stops the pull (`StrandedRenameError`; `.claude/rules/vault-io.md`).

## Writes cut short

- Every engine content write of vault files goes through the journal (`features/sync/recovery/journal.ts`, entry `writeContent` in `features/sync/changes/content.ts`): Obsidian truncates before it writes, so a killed write leaves a prefix that auto-merge takes as a deletion and pushes everywhere. Order: claim (one per pull or vault-restore batch; a pull leaves out new files that are no room snapshot), stage the content, ask `ready` again (an edit saved meanwhile keeps the file: `coldSince`), write, `landed`, release.
- A write cut short is finished, never read as an edit: the plugin's load puts back what was cut short before anything waits on the network (`restoreCutShort`); `compare` finishes pending ones right after the scan, before it waits for the remote (`finishCutShort`). A prefix of the staged copy, or a missing file in a folder that stays, is rewritten; what cannot be finished yet (anything unreadable) leaves the diff as unreadable.
- A download finished or found landed gives the baseline its entry (`BaseStep`), and the diff is taken against that (`withLanded`): on the old baseline it would read as this device's edit and a change made elsewhere since would be pushed back. The step names the storage and vault it was claimed under, which alone take it, and only while their baseline still holds what it held then; adopting the write never moves it.
- A landed write with a step stays in the journal (`land`: never rewritten, staged copy gone) until the baseline holding its step is saved: by its operation (`acknowledge`) or, that save lost, by the runner after its next compare (`settleLanded`). Dropped first, a lost save leaves the old baseline with no record. The runner saves the journal as every operation ends, so an edit before the next compare still finds the write landed.
- A claim over an unfinished write is refused (`UnfinishedWriteError`); writes follow their share's moves and pass to whichever space holds their path (`adopt`).
- A journal that cannot be read stops the plugin loading: read as empty, its writes would pass for edits. Unloaded (`dispose`), it saves nothing more and refuses claims: an operation still running has its state save dropped, so its releases must not reach the file the next instance reads. A concurrency run rejects only once its workers settle (`runWithConcurrency`), so nothing writes behind the error.
