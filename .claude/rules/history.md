# File history, restore and GC

History is one encrypted record per push under `history/`, which GC thins into objects per period. Model, publish order, windows and accepted limits: `features/sync/README.md` (History). Engine invariants: `.claude/rules/sync-integrity.md`; hunk restore: `.claude/rules/hunks.md`.

## Records

- Every push writes `history/p/<id>.enc` before it publishes (`publishManifestWithHistory` in `features/sync/history/publish.ts`), so a won push always has its record; a lost one leaves a sibling the walk never takes. It holds the diff from the snapshot's parent, which is `compareResult.remote`, not `state.baseline` (they differ whenever another device pushed since the last compare).
- A record write is best-effort: a failure warns and never fails the push; the sealed record waits in memory, keyed by storage identity (a share move or token refresh rebuilds the adapter), and the next push writes it first. A failed publish keeps its record waiting: the manifest may have landed, and a sibling costs only GC. A held-back record lands only under the same key and vault and while every blob it names exists (`stillLands`: a root under `objects/` or `recipes/`, which guards its chunks; past a thousand blobs, checked against one listing of each): a sweep or a reset meanwhile would leave it dangling, so it is dropped as a gap. Records and pins are sealed in space paths, so a retry after a move still names the right files.
- History covers vault files, not the vault's configuration folder: `splitTracked` (`historyTracks(untrackedDir(session))` in `features/sync/history/changes.ts`, any casing) leaves `<configDir>/` out of the record and puts every hash that side names in `PushRecord.released`. It is cleanup metadata, never shown nor reachable: GC frees it with the record (`freedHashes`), and the sweep keeps whatever HEAD, a pin or a record still names. A config-only push counts no activity, and the Timeline lists no version without a file change unless pinned (`sessionsOf`; the newest shown walked version takes **Latest** when HEAD is hidden, never an off-walk pin; the calendar still shows when no version is listed). A share splits nothing: its scope names the vault's folder too.
- A record carries both sides (`modified.from` / `.to`, the departed entry on `deleted`) and compares every field (`sameEntry`), so a restore never needs a replay and a missing record leaves a detectable gap, not a corrupted chain.
- A merged record (`composeChanges`, used by the GC model in `features/sync/history/model/`) runs from its first parent to its last push: `deleted` keeps the parent's entry for replay, `deletedLast` the content right before the deletion, and `changeEntries` names both. Merge only chain-contiguous runs.
- Readers walk from HEAD only while a record's `parentId` names the next one (`coverOf` in `features/sync/history/model/cover.ts`); past a gap history is not evidence of anything. Order by the walk, never `createdAt` (clock skew). Storage time (the listing's `modified`) dates a record; an undated push takes its parent's listed time, else the newest.
- Storage times run forward along the walk (`forwardTimes` in `coverOf`), so every period is one run of the chain; a stored object is still split into runs (`runsOf`) and every record ends a candidate, so a sibling may fork from inside a run. Within the horizon a GC build replaces only inputs the walk took whole (an off-walk part may be a sibling or lie behind a gap); a counts build takes its whole group. Counts views merge by the larger per hour (`mergeCounts`, `activityOf`), never a sum.
- `readHistory` (`features/sync/history/remote.ts`) lists `history/` once and decodes only keys it has not seen (records never change, objects are named by content); a key gone between listing and GET (a GC retired it) re-lists once. A listed key that does not decode, a newer format included, is `unreadable`: readers show a gap, GC and deep clean must not run on it.

## Listings

- `listDeletedFiles` walks deletions, never absences: newest first, a path counts only at its newest change along the walk, so a file deleted, recreated and deleted again reports its latest death, and a lagging walk (starting below HEAD's own deletions) never reports an older one; anything back in HEAD is skipped. A merged record restores `deletedLast`, the content right before the deletion.
- Pins outside the walk are diffed against HEAD separately; those rows are `source: "pinned"` and say "last seen", never "deleted": a pin proves the file existed, not when it went. A pin marks a deleted row `pinned` only for the hash it holds.
- `keptUntil` is the earliest time retention may drop a version: the end of its counts group plus the horizon (`keptUntil` in `features/sync/history/model/periods.ts`), null while pinned or without a horizon; `countsBefore` is the time before which every record is past it, and `stagesOf` the resolutions a record passes through for a horizon (the settings ladder, `ladderOf`).
- HEAD without its record sets `lagging`, a walk stopped at a missing parent `truncated`; the UI warns instead of showing an empty vault as an empty trash (`features/source-control/trash/trash-tab.ts`, `features/source-control/timeline/timeline-tab.ts`). The Trash tab and `listDeletedFiles` skip paths the scope no longer includes.
- `listSnapshots` and `getFileHistory` date a version by `at` (`Dating` in `features/sync/history/types.ts`), the storage time of its newest push, and give `res`, the period its key holds; a pin off the walk has only its own clock and `res` null. `listSnapshots` adds `activityOf`, past the horizon too.
- The vault's last-read activity is kept device-local (`ActivityCache` in `features/sync/history/activity-cache.ts`, Obsidian's local storage `mdsync-activity`), keyed by storage identity so another target never shows it; only reads that happen anyway fill it (`listSnapshots`, GC after a vault push), and a read begun before the kept one is dropped. A remote reset or an adopted vault forgets it (`forget`). The settings overview draws it with no request (`features/settings/activity-card.ts`, `buildCalendar` with versions `null`: no resolutions).
- `getFileHistory` emits a file version at the record that wrote it (its `pushes` are that record's), never at a later snapshot that still holds it; content older than the walk is the oldest record's parent, dated at that record's `firstAt`, and not `replayable` (it cannot be pinned). A version's `pinId` is any pin holding its hash, which may be a later snapshot: pin actions go there.
- Timeline sessions are cut from the walk order with pins still in it (`sessionsOf` in `features/source-control/timeline/sessions.ts`): a pin stands alone, so a session's `composeChanges` never skips a link.
- A snapshot is `restorable` only when replay reaches it from HEAD (`replayTo` in `features/sync/history/replay.ts`) or it is pinned. `replayTo` returns null when lagging or past the walk: a partial replay would invent a state.

## Restore

- A restore that puts the vault back is local only: nothing reaches the remote until the person pushes. `planVaultRestore` (`features/sync/history/restore-vault.ts`) is pure, and the confirmation and the operation both run it; the operation re-plans after the confirmation and applies nothing if the plan differs (`sameRestorePlan`).
- It leaves `<configDir>/` alone, neither writing, removing nor counting it (`planVaultRestore`'s `tracks`): replay keeps HEAD's configuration and a pin may hold an older one.
- It removes only paths the scan actually read (an unreadable directory is unknown, not absent), sends removed files to the trash (`trashPath`), and never touches an ignored, out-of-scope or disk-refused path in either direction.
- Its writes run under a journal claim like a pull's (`restoreVault` in `features/sync/runtime/history-service.ts`) and its target manifest keeps only paths the space owns (`ownedFiles`).
- Restore dialogs promise "nothing is pushed until you say so" (`features/diff/ui/restore-modal.ts`); keep that true.

## Pins

- A pin is one object, `pins/<id>.json.enc` (`features/sync/history/pins.ts`): `{ v: 1, manifest, label?, pinnedAt }` with the snapshot's manifest minus `<configDir>/`, so it outlives the records it was replayed from. Nothing else flags it: a pin is on exactly while its object reads.
- `setSnapshotPinned` (`features/sync/history/query.ts`) keeps a readable pin's manifest and replays only for a new one; a pin that cannot be read is rewritten, never trusted. Unpinning deletes the object. Both run on the operation queue (`features/sync/runtime/history-service.ts`).
- A listed pin that does not read (corrupt, or a 1.x bare manifest) is `unreadable` in `readPins`: what it holds is unknown. Decoded pins are cached only by etag: a timestamp may not move on a rewrite. Manifests stay up to `PIN_CACHE_ENTRIES` file entries in all, the info of every listed pin (`readPinInfos`, the Timeline's); both drop pins no longer listed, so a warm read of unchanged pins GETs none.

## GC and deep clean

- Never delete an object reachable from HEAD, from any listed push record or history object (every version it names: `changeEntries`, off the walk too), or from a pin (`reachableHashes` in `features/sync/history/sweep.ts`). If any of those cannot be read, delete nothing (deep clean and verify throw): a bounded blob leak is acceptable, a dangling reference is not.
- Sweep only blobs older than any push in flight: `listDated` (`features/sync/remote/uploads.ts`) lists them with their age and `isSettled` decides, `SETTLED_AFTER_MS` is twice `UPLOAD_TRUST_MS`. Another device may have re-uploaded an old hash for a push it has not published. A storage that cannot report object ages cannot be swept (`listDetailed` is required).
- Deep clean and GC's phase 2 share one sweep (`sweepObjects` in `features/sync/history/sweep.ts`; phase 2 passes `freedOnly`): it needs a published HEAD, deletes nothing written in the last day nor any hash a candidate file younger than a day names (one it cannot read fails closed), and bails if HEAD, the pin listing or a new history key changed since it listed (neither a pin nor a retried record moves HEAD). It deletes no history record, object or pin; settled candidate files go after the sweep.
- A file's root is `objects/<hash>` or `recipes/<hash>`, and the sweep takes both as one hash. Chunks (`chunks/<id>`, shared between files) are no hash: a settled one goes only when no surviving recipe names it, every listed recipe the sweep does not delete counting (young and undated too, so a push in flight keeps the chunks it trusted); phase 2 takes only chunks the recipes it deletes named. Doomed roots are judged once, against one clock. When a chunk could go, a surviving recipe that does not read fails the sweep before any delete; a root never needs another recipe's list. Roots go before chunks, and HEAD, pins and history are rechecked after every read, right before the deletes. Recipe reads are kept by etag (`chunksNamed` in `features/sync/content/closure.ts`).
- GC (`collectHistoryGarbage` in `features/sync/history/gc.ts`) runs after a push this device published, at most every 10 min per space, on the quiet queue (`MaintenanceService.afterPush`); a failure only logs. Without object ages (`listDetailed`) it does nothing.
- The horizon is this device's **Keep history for** (`fileHistoryKeep`, a key of `HISTORY_KEEP_MS` in `core/constants.ts`, named by `HISTORY_KEEP_TEXT`; `forever` is `null`), read per session in `app/session-factory.ts`. Each device's GC applies its own, so the shortest wins.
- Phase 1 stops on any unreadable history key: a gap only this run sees would let counts or the horizon take what lies behind it. Each planned object is written under the digest of its whole content, `consumed` included, and read back before anything it replaces goes (`writeHistoryObject`); only keys this run listed are deleted, and what the verified object names in `consumed`, never the plan. Readers recompute every object's key: one whose content does not match is unreadable, never trusted to consume anything.
- Phase 1 deletes no blob: the hashes its retired keys named and the verified objects do not go to `history/g/<runId>.enc` before any delete. Phase 2 sweeps a candidate file only once it is settled (`isSettled`, `SETTLED_AFTER_MS`), so a pin or record written around phase 1 is listed by then and keeps its blobs. It runs only once a candidate is a day past settling (`sweepDue` in `gc.ts`) and then takes every settled one: its full listing of `objects/`, `recipes/` and `chunks/` costs a request per thousand blobs, so it runs about once a day, and freed versions stay one to two days. When every freed hash is still reachable it deletes only the settled candidate files and lists nothing. `readHistory` lists `history/g/` in its one call.
- `planGc` deletes only: keys a present object consumes, a settled push that lost the guard (its parent's chain child is another id), another vault's settled keys, and settled keys off the walk whose newest record is past the horizon.
- Maintenance lists only `objects/`, `recipes/`, `chunks/`, `pins/` and `history/` of its own space; a reset deletes chunks after every root.

## Format fence

- Every manifest carries `MANIFEST_VERSION` 3 (`buildManifest`), and `fetchRemoteManifest` refuses a higher one: a 1.x client stops at HEAD before any GC or deep clean. Raise it whenever an older client would destroy what the new format keeps.
- 1.x history is deleted, never read: after the first published push of a session per space, history on or off, `clearLegacyHistory` (`features/sync/history/legacy.ts`) deletes every pin that decrypts to a bare manifest, then `history.json.enc`; a failed run is retried at the next push. Pins are scanned even without the log (an interrupted reset can leave them, and one blocks every sweep); a pin it cannot decrypt stays.
- A sweep refuses a HEAD below `MANIFEST_VERSION`: 1.x clients still sync there, and their history names what looks orphaned.
