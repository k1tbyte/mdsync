# Sync invariants

Hard data-integrity rules of the engine. Breaking one silently corrupts user
data or publishes remote deletions. Every change in these areas needs tests.

- **Hunk source of truth**: a hunk operation must take both texts from `loadHunkSides`, the same function the projection uses, and must verify the sha256 of each side before it applies an index. A view that diffs one pair of texts while the operation recomputes from another will apply the wrong hunk.
- **Baseline advance**: the baseline may only move for paths an operation actually wrote. Adopting a whole published or remote manifest silently claims every file this device has not downloaded, and the next push publishes them as deletions.
- **Remote reads are complete**: matching snapshot ids do not make a partial baseline a remote manifest. HTTP 304 must use the complete cached response under the same storage adapter and encryption key. Stale reads may use a complete head actually published by this session, never the baseline.
- **Configuration resets are not file deletions**: reset generations are scoped by configuration directory and category. A newer generation forgets that category's baseline files and folders, preserving local files on every device. Ordinary publishes retain generations. Reset manifests require version 2 so older clients refuse them.
- **Disabled scope is untouched**: excluded configuration files and empty folders remain in the remote manifest and baseline during ordinary operations. Only an explicit category reset forgets their baseline.
- **History is a change log, not an archive.** `history.json.enc` holds one record per push, each the diff from that snapshot's *parent* - which is `compareResult.remote`, not `state.baseline`; the two differ whenever another device pushed since the last compare. Records carry both sides (`modified.from`/`.to`, and the departed entry on `deleted`) so a restore never needs a replay and a lost update leaves a detectable gap instead of a corrupted chain. Walk the chain only while `entry.parentId === next.id` (`contiguousLength`); past a gap the log is not evidence of anything.
- **Deleted-file listing walks deletions, never absences.** `listDeletedFiles` collects `changes[snapshot].deleted` newest first and keeps the first hit per path, so a file deleted, recreated and deleted again reports its latest death; anything back in HEAD is skipped. Pinned snapshots outside the walked chain are diffed against HEAD separately, and those rows say "last seen", not "deleted" - a pin proves the file existed, not when it went. A log that lags HEAD sets `lagging` rather than reporting an empty vault as an empty trash.
- **Hunk indices belong to one patch.** The history diff numbers its hunks from `computeHunks(version, current)`, so `restoreHistoryHunks` must compute in that same order and invert the selection (`applyHunks` takes the right side for selected hunks, so keeping one hunk on the version's side means selecting all the others). It also verifies the working copy's sha256 against the one the view drew, or a file edited since then gets a stale index applied.
- **A restore that puts the vault back is local only.** `planVaultRestore` is pure and both the confirmation and the operation run it, the operation re-planning after the user confirms. It only removes paths the scan actually read - an unreadable directory means unknown, not absent - and never touches an ignored path in either direction. Nothing reaches the remote until the user pushes.
- **GC reachability under the change log**: never delete an object reachable from HEAD, from a retained change record, or from a pinned snapshot's manifest. If any of those cannot be read, set `skippedObjectSweep` and delete no objects at all - a bounded blob leak is acceptable, a dangling reference is not. Pins keep their own full manifest under `pins/` precisely so they outlive the chain; write that manifest *before* setting the flag, or GC will believe objects are protected that nothing references.
- **Unreadable is not absent**: a file or directory the scan could not read is reported in `snapshot.skipped` and excluded from the diff. Treating it as missing turns a locked file into a remote deletion.
- **Diff views must never load unshowable content**: classify sides from `adapter.stat()`, manifest entry sizes, and `KNOWN_BINARY_EXTENSIONS` before reading or downloading anything (see `src/sync/projection.ts`). Keep this invariant when touching diff/merge code paths.
- **A live room is seeded once, and only while it has no log.** The session sends `Seed` from disk only on a `State` with `head == 0`; the hub appends it only into an empty log and answers a losing seed with the whole room, and the seed is applied locally only on its `Echo`. An empty room *with* a log is a deleted note: seeding it would resurrect it, two seeds would double it.
- **Disk enters a live room only by three-way merge.** `mergeThreeWay(base, disk, room)`, then `patchYText` as inserts and deletes on code points. Never delete-all + insert and never a diff from room to disk: both overwrite what others wrote meanwhile. A conflict keeps both sides, the room's first.
- **A `live` mark means the content is exactly that room's text at `seq`.** Only a hash equal to the note's agreed text earns it, and an open room with anything pending or unacked marks nothing: the path waits for the next push. Marks are `{doc, gen, seq}` with `doc` the note's generation-0 docId, ordered by `(gen, seq)`: a rebuilt room follows every snapshot of the one before. A mark never replaces the remote's mark of the same note at an equal or higher order. Two marks of one note are settled by that order, never merged (`sync/live-notes.ts`).
- **The file sync never writes a note whose room is open.** The incoming version goes to the room (`LiveNotes.absorb`: its own snapshot is already there, anything else is merged three-way against the baseline). The room saves the result through the note's editor before the baseline takes the remote entry, so the baseline never claims a version the disk lacks. A room behind a snapshot of itself answers `later`: nothing moves. So does a note still joining its room while the hub is up; with the hub down it is an ordinary file. A marked version written to a closed note becomes its agreed text, disk first, then the base. Reconcile reads the base first, so it never pairs a newer base with an older disk.
- **A live snapshot is taken only from a settled document.** With nothing pending or unacked the Y.Doc is exactly the room at `lastSeq`; a snapshot holding an unacked edit would hand newcomers text the current followers never got. Only the lowest client id sends it, and the hub refuses one not newer than the snapshot it holds.
- **A room is rebuilt in one hub step, or not at all.** `Rotate` carries the sender's `lastSeq` as `upto`; the hub seeds the successor and seals the old room only if the log is still at `upto`, the room is not moved and the successor has no log. Otherwise an edit could be acked in the old room and missing from the new one. Only a settled session rotates, a follower of a pointer never seeds, and a pointer other than `docIdFor(path, gen + 1)` leaves the note to the file sync.
- **An update leaves the unacked FIFO only on its echo.** Everything unacked is resent on the next socket's `State`; frames queued under a dead socket's epoch never act on the new one. `head < lastSeq` means the room lost its log: resubscribe from 0 and resend the full state.
