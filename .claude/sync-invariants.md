# Sync invariants

Hard data-integrity rules of the engine. Breaking one silently corrupts user
data or publishes remote deletions. Every change in these areas needs tests.

- **Hunk source of truth**: a hunk operation must take both texts from `loadHunkSides`, the same function the projection uses, and must verify the sha256 of each side before it applies an index. A view that diffs one pair of texts while the operation recomputes from another will apply the wrong hunk.
- **Baseline advance**: the baseline may only move for paths an operation actually wrote. Adopting a whole published or remote manifest silently claims every file this device has not downloaded, and the next push publishes them as deletions.
- **Remote reads are complete**: matching snapshot ids do not make a partial baseline a remote manifest. HTTP 304 must use the complete cached response under the same storage adapter and encryption key. Stale reads may use a complete head actually published by this session, never the baseline.
- **Configuration resets are not file deletions**: reset generations are scoped by configuration directory and category. A newer generation forgets that category's baseline files and folders, preserving local files on every device. Ordinary publishes retain generations. Reset manifests require version 2 so older clients refuse them.
- **Disabled scope is untouched**: excluded configuration files and empty folders remain in the remote manifest and baseline during ordinary operations. Only an explicit category reset forgets their baseline.
- **History is a change log, not an archive.** `history.json.enc` holds one record per push, each the diff from that snapshot's *parent* - which is `compareResult.remote`, not `state.baseline`; the two differ whenever another device pushed since the last compare. Records carry both sides (`modified.from`/`.to`, and the departed entry on `deleted`) so a restore never needs a replay and a lost update leaves a detectable gap instead of a corrupted chain. Walk the chain only while `entry.parentId === next.id` (`contiguousLength`); past a gap the log is not evidence of anything.
- **Deleted-file listing walks deletions, never absences.** `listDeletedFiles` collects `changes[snapshot].deleted` newest first and keeps the first hit per path, so a file deleted, recreated and deleted again reports its latest death; anything back in HEAD is skipped. Pinned snapshots outside the walked chain are diffed against HEAD separately, and those rows say "last seen", not "deleted" - a pin proves the file existed, not when it went. A log that lags HEAD sets `lagging` rather than reporting an empty vault as an empty trash.
- **Hunk indices belong to one patch.** The history diff numbers its hunks from `computeHunks(version, current)`, so `restoreHistoryHunks` must compute in that same order and invert the selection (`applyHunks` takes the right side for selected hunks, so keeping one hunk on the version's side means selecting all the others). It also verifies the working copy's sha256 against the one the view drew, or a file edited since then gets a stale index applied.
- **A restore that puts the vault back is local only.** `planVaultRestore` is pure and both the confirmation and the operation run it, the operation re-planning after the user confirms. It only removes paths the scan actually read - an unreadable directory means unknown, not absent - and never touches an ignored path in either direction. Nothing reaches the remote until the user pushes.
- **GC reachability under the change log**: never delete an object reachable from HEAD, from a retained change record, or from a pinned snapshot's manifest. If any of those cannot be read, set `skippedObjectSweep` and delete no objects at all - a bounded blob leak is acceptable, a dangling reference is not. Pins keep their own full manifest under `pins/` precisely so they outlive the chain; write that manifest *before* setting the flag, or GC will believe objects are protected that nothing references.
- **Unreadable is not absent**: a file or directory the scan could not read is reported in `snapshot.skipped` and excluded from the diff. Treating it as missing turns a locked file into a remote deletion.
- **Diff views must never load unshowable content**: classify sides from `adapter.stat()`, manifest entry sizes, and `KNOWN_BINARY_EXTENSIONS` before reading or downloading anything (see `src/sync/projection.ts`). Keep this invariant when touching diff/merge code paths.
- **A drawing is its scene.** An Excalidraw file (front matter `excalidraw-plugin`) also holds the saving device's zoom, scroll and tool, so two devices save one drawing as different bytes. The scanner fingerprints the scene into `scene` (`drawing/scene.ts`: the text outside the drawing block plus each live element's `id:version:versionNonce`) and the diff takes equal scenes for equal content; otherwise every save pushes. Conflicts merge by element (`mergeDrawings`: the higher version wins, then the lower nonce; an element one side dropped goes unless the other changed it), never by lines, which yields a scene that no longer opens. Notes above the data changed on both sides stay a conflict. A drawing never earns a `live` mark: its file may lag its room.
- **Authorship is set only at publish.** `publishFileMap` runs `attribute` (`sync/authors.ts`): a changed hash takes the publisher, anything else keeps its parent's `by`. The `authors` table only grows, so an index read from any earlier manifest or baseline still names the same key; `by` is never content, so equality checks ignore it (`sameEntry`).
- **Every path belongs to exactly one space.** `spaceOf` picks the deepest root holding the path, else the vault. A space's scope owns its root's subtree minus the roots nested in it (`nestedRoots`); the vault treats share roots like a local ignore, so its entries there stay frozen until the vault's next push, which leaves them out of the manifest (`sync/foreign.ts`): frozen, they would hold the folder's blobs for good. The change record still lists them as `deleted`, so history GC sweeps the blobs once it rolls off; the Trash tab and a vault restore skip paths the vault no longer owns. A baseline forgets frozen entries the remote no longer has (`forgetDroppedForeign`, each refresh) so closing the share never reads them as remote deletions; entries the remote still lists stay, so an edit made before closing is a plain modify. A forgotten entry whose share here has no baseline of the path yet moves to the vault slot's `shareBases`, the live merge base of a note that just became a share (`baseTextOf`), never part of the baseline; it leaves once the share holds the path or the folder is the vault's again. A share's root folder is its mount point and belongs to no space: never published, never removed.
- **The partition is fixed per refresh.** The controller asks `host.spaces()` once, inside the queue at the start of a refresh (the host pulls space records then), and routes every operation by that list until the next refresh. `openSession(space, partition)` builds scopes from that list alone: a record that arrives mid-cycle must not turn a root back into vault content that was never scanned, or push publishes its files as deleted.
- **A share never publishes the loss of all its files.** When a share's scan finds nothing while its baseline still holds files (its folder was deleted or moved away on this device), `compare` throws `SpaceGoneError` (`assertSpacePresent` in `sync/space.ts`): the share is that device's error, detached there, never an empty folder for everyone. The vault itself is not guarded.
- **Closing a share is a record edit, never a deletion of files.** Records are tombstoned (`closed`, `rev + 1`) so no device republishes them; a closed record leaves the partition from the next refresh, and its root returns to the vault scope with its files. Stop sharing then empties the share's own storage through the operation queue (`deleteShareObjects` refuses the vault). Every close, here or seen from elsewhere, and leaving shares with the vault storage forget the share's state by its id (`StorageState.space`), needing no session: a participant's slot keeps one identity across re-accepts, so a later reopen at any root would otherwise read the old baseline as deleted files. Stop sharing refreshes before it deletes, so an operation queued for the share is refused instead of pushing its objects back.
- **A paused share stays in the partition.** Pause is device-local (`settings.pausedSpaces`, never published); `spacesOf` marks the space `paused`, the refresh skips it and every session refuses it, reads such as history too (`OperationRunner.openSession`), but its root stays out of the vault scope. Dropping it from the partition would hand the folder to the vault and publish it there.
- **A moved root moves on every device before any scan.** A rename of a share root (or a folder above it) edits the record (`moveRoot`, `rev + 1`) and invalidates in the same tick; results begun before the invalidation are dropped (refresh epoch), so auto-push never acts on the old partition. A device that learns of the move keeps the folder where it is (`settings.localRoots`, saved with the records) and `plugin/share-moves.ts` moves it inside `host.spaces()`, before the partition is fixed; a blocked move keeps the share syncing at the old root. A closed share's folder is the vault's and is never moved. An old root must never turn into vault content that holds the share's files.
- **Vault-wide listings stay inside `objects/` and `pins/`.** Shares live under `<prefix>/shares/<id>/` and records under `<prefix>/spaces/`, inside the vault's prefix; GC, verify and reset must never list or delete beyond their own folders.
- **A space's remote paths are relative to its root; local ones never are.** Manifest, history log and pin manifests are translated only in their codec functions (`sync/space-paths.ts`, called from `sync/manifest.ts` and `sync/history/store.ts`); every read and write of those blobs goes through them, hash-only readers included. Each scan carries forward the hash-cache entries its space does not own, so one space's persist never drops another's. A share's `state.json` slot records the root its baseline sits under (`StorageState.root`); `projectSession` re-roots it once after a move (`manifestMoved`), and an unmoved baseline keeps its reference so the persister still debounces.
- **A note is live only in its own space's room.** The room is named under that space's keys by the path inside its root (`docIdIn`), and its frames go only on that space's slot (`HubConnection.space`). A note whose space changes (shared, paused, new key) leaves its room; the file sync of one space answers `later` for a note whose room belongs to another. Paused shares stay cold. A read-only person's notes follow their room and never write it (`FollowerSession`): a change made there, or an incoming version the room lacks, leaves the note to the file sync; the hub refuses every write from a read-only grant (`Refused`).
- **A live room is seeded once, and only while it has no log.** The session sends `Seed` from disk only on a `State` with `head == 0`; the hub appends it only into an empty log and answers a losing seed with the whole room, and the seed is applied locally only on its `Echo`. An empty room *with* a log is a deleted note: seeding it would resurrect it, two seeds would double it. An empty room behind what the device knows of it (its agreed seq in that generation, or a successor it was pointed at) lost its log and is never seeded.
- **Disk enters a live room only by three-way merge.** `mergeThreeWay(base, disk, room)`, then `patchYText` as inserts and deletes on code points; a shared run under 10 characters between two changes is re-inserted with them only when that saves an op, so a rewritten sentence is one replacement, not an item per shared letter (a device that edits inside such a run in the same moment lands beside the re-inserted copy). Never delete-all + insert and never a diff from room to disk: both overwrite what others wrote meanwhile. A conflict keeps both sides, the room's first; only overlapping hunks (or inserts at one point) conflict, neighbouring lines merge. A drawing merges by element against its agreed stamps; what the file dropped unchanged becomes a tombstone in the room, since a saved file leaves deleted elements out.
- **A `live` mark means the content is exactly that room's text at `seq`.** Only a hash equal to the note's agreed text earns it, and an open room with anything pending or unacked marks nothing: the path waits for the next push. Marks are `{doc, gen, seq}` with `doc` the note's generation-0 docId, ordered by `(gen, seq)`: a rebuilt room follows every snapshot of the one before. A mark never replaces the remote's mark of the same note at an equal or higher order. Two marks of one note are settled by that order, never merged (`sync/live-notes.ts`).
- **The file sync never writes a note whose room is open.** The incoming version goes to the room (`LiveNotes.absorb`: its own snapshot is already there, anything else is merged three-way against the baseline). The room saves the result through the note's editor before the baseline takes the remote entry, so the baseline never claims a version the disk lacks. A room behind a snapshot of itself answers `later`: nothing moves. So does a room that closed or moved while the incoming text was fetched, and a view that could not save. So does a note still joining its room while the hub is up; with the hub down it is an ordinary file, and every view showing it is readied for the write (`expectWrite`): Excalidraw takes the first write after its own save for that save's. A marked version written to a closed note becomes its agreed text, disk first, then the base. Reconcile reads the base first, so it never pairs a newer base with an older disk.
- **A live snapshot is taken only from a settled document.** With nothing pending or unacked the Y.Doc is exactly the room at `lastSeq`; a snapshot holding an unacked edit would hand newcomers text the current followers never got. Only the lowest writer's client id sends it (a reader's awareness says `follows`), and the hub refuses one not newer than the snapshot it holds.
- **A room is rebuilt in one hub step, or not at all.** `Rotate` carries the sender's `lastSeq` as `upto`; the hub seeds the successor and seals the old room only if the log is still at `upto`, the room is not moved and the successor has no log. Otherwise an edit could be acked in the old room and missing from the new one. Only a settled session rotates, a follower of a pointer never seeds, and a pointer other than `docIdFor(path, gen + 1)` leaves the note to the file sync.
- **An update leaves the unacked FIFO only on its echo.** Everything unacked is resent on the next socket's `State`; frames queued under a dead socket's epoch never act on the new one. `State` names its log: another name, or a head behind what the session knows, means the room lost it. The note then rotates onto its next generation from its own text, never refills the old room: seqs would restart under marks, and a log regrown from another device's disk would double the text.
- **A move acts whole.** `pairMoves` (`sync/moves.ts`) pairs a gone path with a new one of the same baseline hash in one space (else by file name, only where one to one); anything unclear stays a delete plus an add. The other side's edit of the old path follows the file instead of conflicting. Push, pull and revert take both paths when asked for one (`withMoves`, `pullMoves`). A pull renames (`renameLocal`), never over a file that appeared at the new path since the compare, and never a note an open room holds; folders it emptied go (`removeEmptied`), never the space root nor one the remote keeps. Diff views of a move apply no hunks: their sides sit at two paths.
