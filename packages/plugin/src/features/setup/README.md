# Setup wizard

One modal stepper takes a fresh install to a syncing vault: storage (Cloudflare R2 from a token by default), passphrase, features (when to sync, history, what of Obsidian syncs), relay (deployed from the plugin) and first sync. It replaces "configure first" toasts with a way into the right step. Constraints: `.claude/rules/settings-setup.md`.

## Entry points

- `openSetupWizard(plugin, step, onClosed)` (`features/setup/wizard.ts`), reached through `plugin.openSetup(step?)` in `main.ts`; the callback refreshes the settings tab, the Changes tab and the status bar the wizard changed under. One wizard at a time: asking again moves the open one to `step`. `closeSetupWizard()` runs on unload.
- Without a step it opens where this device stands (`firstStep` in `features/setup/step-state.ts`): no storage -> Start; otherwise the first step of the `new` path not done; else Ready. Never stored: `isStepDone` reads the settings, so the wizard agrees with the settings tab.
- Callers: a fresh install (`main.ts`: `loadData()` returned null, settings saved first so closing it does not bring it back, then on layout ready); command `open-setup-wizard` ("Set up sync", `app/commands.ts`); the **Setup wizard** button of the settings overview (`features/settings/overview.ts`); the status menu; the notice **Set up** when a sync has no storage or the saved connection cannot be read; the relay section (`ESetupStep.Relay`); the link menu and `openShareLink` without a relay (`ESetupStep.Relay`); the Changes tab prompt (`features/source-control/setup-prompt.ts`, also `ESetupStep.Import`).

## Paths and steps

`features/setup/step-state.ts` holds `ESetupStep`, `ESetupPath` and `PATH_STEPS`.

- Start (no stepper, `features/setup/steps/start-step.ts`): **Start syncing this vault** (path `new`), **Connect to a vault set up on another device** (path `join`, first and highlighted on a phone, which is rarely the first device), **Accept an invite to a shared folder** (hands off to `openInvite` of spaces, closes), **Not now**.
- `new`: Storage -> Passphrase -> Features -> Relay -> Ready. `join`: Import -> Features -> Relay -> Ready (the setup link usually brings the relay; a done step shows its summary and **Next**).
- Back walks the path; a step may undo inside itself first (`StepView.back`). **Skip** shows on the optional Relay step while it is not done. **Next** shows only once the step is done and `blocksNext()` is false; until then the step's own button moves on, so no bare disabled Next.

| Step | File | What it does |
|---|---|---|
| Storage | `features/setup/steps/storage-step.ts` | **Cloudflare R2** (recommended) or **Other storage**. R2: token form, then `useR2` (`features/storage/cloudflare/r2-select.ts`): bucket `mdsync-vaults` via `ensureBucket`, S3 keys derived from the token (`r2Keys`), `prefix` = vault-name slug plus a hash so two vaults on one account stay apart, active kind S3, then `testConnection`. `R2NotEnabledError` shows **Open R2** and **Try again**. A refused token (`isRefusedToken`) is forgotten so the form returns, and the new token lands in the same prefix. Warns that deleting the token in Cloudflare stops sync. Other: `backendSection` as in settings; **Continue** runs `testConnection` and blocks on failure |
| Passphrase | `features/setup/steps/passphrase-step.ts` | `passphrase.unlock()` first: a saved one that opens the vault moves on by itself (`wizard.moveOn()`: to where the device stands when the wizard opened on this step, else the next one), unless the step was entered by Back after it was done, else `vaultHasKey()`: none -> new passphrase and confirm held to `weakPassphrase` ("nobody can reset it"); present -> "enter the passphrase from your other device". A wrong one (`PassphraseRotatedError`) is dropped and shown inline. Storage unreachable offers **Try again**, and **Update keys** (`openStorageRefusedModal`) when the storage refused R2 keys |
| Import | `features/setup/steps/import-step.ts` | setup link and passphrase, then `transfer.importWith(link, passphrase)`. No prompt modal and no typed `IMPORT`: the step says what it replaces (storage, what syncs, automation and history, the relay) and the button is the consent |
| Features | `features/setup/steps/features-step.ts` | always done: its values are the settings. **When to sync** presets (`ESyncMode` in `features/setup/feature-choices.ts`, read by `syncModeOf`, written by `syncModePatch`): Manual turns autosync, push after change and real-time sync off; Automatic turns the first two on with a 5 minute interval when it was 0; Instant adds real-time sync, which without a relay waits for the relay step (`useRelay`) and lapses, shown and on activation alike, once the settings turn Manual (`shownSyncMode`, `enablesRealtime`). The pick is kept on the wizard (`Wizard.syncMode`), one for every wizard of the launch since a deploy outlives its wizard: a relay connected or deployed after Manual or Automatic leaves real-time sync off (`enablesRealtime`); a mode never picked counts as Instant. Push after change alone reads as Automatic. **Keep history** and **Keep for**; core settings, hotkeys, themes and snippets, enabled plugins, and the Plugins level and **Per plugin** rows of the settings tab (`pluginLevelRows`, without **Clear on remote**); live editing and the open note (`SETUP_FIELDS` of `features/settings/sections/realtime.ts`) once real-time sync is on. On `join` it says the values came with the link and apply to this device only |
| Relay | `features/setup/steps/relay-step.ts`, `features/setup/steps/relay-deploy-view.ts` | see Relay below |
| Ready | `features/setup/steps/ready-step.ts` | with storage, the first sync (`features/setup/steps/first-sync.ts`): a compare (`controller.refresh()`) that moves nothing (one that ends with no result, as when the passphrase prompt was cancelled, says so and offers **Try again**, never "all set"), then counts to upload, to download and in conflict, **See the files** (Changes) and **Sync N files** = `controller.refreshAndAutoSync(true)`, the scheduled cycle: it merges notes whose changes do not overlap, and a conflict left holds the whole sync, as Push all and Pull all refuse to run past one. Conflicts with no `baselineHash` (both sides added the file, as on a second device's first sync) can never merge on their own: the step names them and offers only **Choose in Changes**. After a held sync it says what waits (**Waiting for your choice**). Below, the summary rows (storage, encryption, relay, when to sync, history). While something is left to move or choose the footer's **Done** is not the accent button (`quietFooter`). Nothing left to move -> the done guide (`features/setup/steps/done-tour.ts`): where the status bar (desktop), panel, file tree marks and editor margin are, the words push, pull, compare and conflict, **Show setup link** (`showSettingsTransferExport`) and, without a relay, **Add a relay** |

## Modules

- `features/setup/wizard.ts` - modal shell, `STEPS` table (label, icon, `create*Step`), stepper header, Back, Skip and Next footer. `Wizard` is what steps get: `redraw(fromTop?)` (`fromTop` when the content was replaced whole), `next`, `moveOn`, `choose(path)`, `close`, `isShowing(view)`, `isLive()`, `currentPath()`.
- `features/setup/feature-choices.ts` - the Features step's sync mode presets over the automation settings, pure.
- `features/setup/steps/first-sync.ts`, `features/setup/steps/done-tour.ts` - the Ready step's first sync preview and the guide it ends on.
- `features/setup/stepper.ts`, `features/setup/choice-card.ts`, `features/setup/form.ts` (`actionRow`, `busyLine`), `features/setup/passphrase-meter.ts`, `features/setup/run-action.ts` (busy and error wrapper for every async button), `features/setup/styles/`.
- `features/setup/steps/cloudflare-token.ts` - the token form shared by the Storage and Relay steps: **Open Cloudflare** (`tokenTemplateUrl`, permissions preselected), paste, account picker when the token reaches several accounts, then `connectCloudflare`.
- Non-UI logic lives with its domain: Cloudflare login and R2 in `features/storage/cloudflare/`, deploy and update in `features/relay/deploy/` and `features/relay/update/`, `importWith` in `features/transfer/`, `unlock` and `vaultHasKey` in `PassphraseManager` (`features/sync/remote/passphrase-manager.ts`).

## Relay step

- Choices: **Deploy to my Cloudflare** (recommended), **I already have a relay** (URL and secret, **Connect** runs `testRelay`, settings saved only on success and only while that manual view is still showing), or **Skip**, which lists what stays off (instant sync, live editing, invites, share links). With a relay already set the step shows its version against the bundled one and **Update**.
- Deploy (`relayDeployView`): token form if none, then the account's workers and workers.dev subdomain (`accountRelays`). `planRelay` decides: this device's relay on the account that answers -> update in place with its secret; no relay and the default name free -> new relay with a random secret; otherwise ask. Asking offers **Update it** (type the existing relay's secret, checked with `testRelay` before deploying), **Use another token** when this device's relay is not on the account, and **Deploy new** with a name (first free `mdsync-relay-N` proposed, `relayNameError` validates).
- Progress is the `ERelayDeployStep` checklist (workers address, storage, share page files, relay code, public address) plus **Answering**, then `activateRelay` polls `/status` until `version === RELAY_VERSION`, about 3 minutes (`WAIT_MS`), then **Check again**. On success `relayUrl`, `relaySecret` are saved at upload and `realtimeSync` turns on once it answers (`useRelay`), unless Manual or Automatic was picked in Features.

## Lifetime and races

- The deploy outlives the wizard: `deploying` in `features/relay/deploy/deploy-flow.ts` is module-level. A wizard closed mid-deploy leaves it running; a reopened one shows "still deploying from earlier" and attaches (`runningRelayDeploy`) instead of starting a second. The URL and secret are saved the moment the worker holds the secret (`onUploaded`), so a closed wizard never loses a live relay's secret.
- A deploy that broke off is remembered with its secret (`failedRelay`); **Try again** repeats it with that secret. It is used only while no relay is configured, so a stale secret cannot replace a working relay.
- Late results move on only from the step still on screen (`wizard.isShowing(view)`); `isLive()` guards redraws after a close. An edited token or secret is compared with what was sent before the result is applied.
- The settings tab is its own document: a wizard left in another one is hidden or went away with it, so `openSetupWizard` closes it and opens anew.

## Recovery

- No storage when sync runs: notice **Set up** (`onNoStorage` from `app/bootstrap.ts`), never a modal from a background sync.
- Saved connection unreadable (vault copied, keychain reset): notice **Set up** on layout ready; the sealed envelope is kept untouched until storage is set up again (`app/settings/envelope.ts`).
- Storage refused the keys: Passphrase step **Update keys**, or the settings storage fields for other backends. R2 keys derive from the Cloudflare token, so a rolled token needs `rekeyR2`; the saved login is replaced when it was that token.
- Relay refused or lost: the Relay step, or **Settings → MDSync → Connection → Update relay**, which opens the wizard at Relay and updates in place.
